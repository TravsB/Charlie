# NEXUS AI — Detailed Technical Architecture



Architecture decisions finalized

&#x20;TECHNICAL BLUEPRINT · V1.0



We've now established the three architectural decisions:

| Area            | Final decision                                           |
| --------------- | -------------------------------------------------------- |
| Agent execution | Hybrid: parallel and sequential                          |
| Team Leader     | Supervised autonomy                                      |
| Deployment      | Cloud-based                                              |
| AI connectivity | APIs and supported direct integrations                   |
| Architecture    | Modular monolith, designed for future service separation |

Now I want to turn this into something a developer could actually use to start building.

The guiding engineering principle will be:

NEXUS AI should separate intelligence, execution, integrations and user control.

That separation is what will allow us to add new AI providers, agent roles and capabilities without rebuilding the entire platform.

# 1. Detailed system architecture

Let's define the actual runtime components.

## NEXUS AI · Runtime architecture

WEB APPLICATION

API & IDENTITY LAYER

FastAPI · Authentication · Authorization · Request validation

APPLICATION CORE

ORCHESTRATION RUNTIME

INTEGRATION & EXECUTION

Agent Runtime

Task execution and tool management

Provider Gateway

Model routing and adapters

INFRASTRUCTURE

PostgreSQL · Redis · Object Storage · Workflow Engine · Observability

There is one important implementation distinction here: the application core handles business rules, while the orchestration runtime handles the actual execution of AI work. We should avoid mixing those responsibilities.

## 2. Backend module specifications

I propose the following modules.

| Module     | Responsibilities                                 |
| ---------- | ------------------------------------------------ |
| Identity   | Users, sessions, permissions                     |
| Projects   | Project creation and lifecycle                   |
| Teams      | Team configuration and membership                |
| Agents     | Agent definitions, capabilities and instructions |
| Providers  | Provider connections and available models        |
| Commands   | User instructions and command interpretation     |
| Planning   | Task decomposition and dependencies              |
| Scheduling | Agent assignment and execution capacity          |
| Execution  | Running tasks and handling results               |
| Messaging  | Agent-to-agent communication                     |
| Memory     | Project context and retrieval                    |
| Approvals  | Human decision checkpoints                       |
| Evaluation | Quality assessment and revisions                 |
| Artifacts  | Files, reports and generated outputs             |
| Usage      | Tokens, costs, quotas and limits                 |
| Monitoring | Logs, events, metrics and traces                 |

Each module should own its business logic and expose well-defined interfaces to other modules.

For the initial implementation, these modules can live inside one FastAPI application.

Here is how execution works:

1. The Team Leader generates a structured task plan.
2. The dependency resolver identifies tasks that can run concurrently.
3. The scheduler assigns available agents.
4. Agents execute their assignments.
5. Results are stored as artifacts.
6. Dependent tasks become eligible when their prerequisites are satisfied.
7. The Critic evaluates the results.
8. The Team Leader presents the completed work for user approval.

We should implement a finite-state machine for task execution.

Task lifecycle

PENDING

READY

ASSIGNED

RUNNING

REVIEW

COMPLETED

Additional states

- BLOCKED: Waiting for dependencies.
- NEEDS_APPROVAL: Waiting for the user.
- REVISION_REQUIRED: Requires more work.
- FAILED: Execution failed.
- CANCELLED: Stopped by the user.

We must enforce valid state transitions in the backend, not rely on agents to report their own status accurately.

# 4. Agent architecture

Now let's define what an agent actually is inside NEXUS AI.

An agent should not simply be a prompt sent to an AI model. It should be a configurable execution unit.

Every agent should have:

| Property     | Description                           |
| ------------ | ------------------------------------- |
| Agent ID     | Unique identifier                     |
| Name         | Display name                          |
| Role         | Researcher, Developer, Analyst, etc.  |
| Instructions | Its system-level role definition      |
| Model        | Assigned AI model                     |
| Capabilities | What it can do                        |
| Tools        | Which tools it can access             |
| Permissions  | What actions it is allowed to perform |
| Memory       | Relevant working context              |
| Status       | Current execution state               |

## Agent configuration example

A Researcher agent might be configured like this:

```
{
  "name": "Market Researcher",
  "role": "researcher",
  "provider": "openai",
  "model": "configured-model-id",
  "capabilities": [
    "web_research",
    "source_verification",
    "summarization"
  ],
  "permissions": {
    "read_project_memory": true,
    "write_project_memory": false,
    "send_agent_messages": true,
    "execute_external_actions": false
  },
  "execution": {
    "max_retries": 2,
    "timeout_seconds": 180,
    "requires_review": true
  }
}
```

This configuration is illustrative. Provider and model identifiers will be validated against actual registered connections.

## The six initial agent definitions

| Agent       | Primary capability        | Secondary capability |
| ----------- | ------------------------- | -------------------- |
| Team Leader | Planning and coordination | Quality management   |
| Researcher  | Information retrieval     | Source verification  |
| Analyst     | Data analysis             | Reasoning            |
| Creator     | Content production        | Document generation  |
| Developer   | Programming               | Technical design     |
| Critic      | Evaluation                | Error detection      |

The Team Leader should be a special orchestration role. It can use an AI model to reason and plan, but the actual execution authority remains in the deterministic backend.

This is important: the AI recommends actions; the platform validates and executes permitted actions.

# 5. AI provider integration architecture

We need a provider abstraction that supports multiple AI systems.

I propose this structure:

```
Provider Gateway
│
├── Provider Registry
│
├── Model Registry
│
├── Credential Manager
│
├── Capability Resolver
│
├── Routing Engine
│
└── Provider Adapters
     ├── OpenAI Adapter
     ├── Anthropic Adapter
     ├── Google Adapter
     └── Custom Adapter
```

Each adapter implements a common interface.

### Example Python interface

```
from abc import ABC, abstractmethodfrom typing import Anyclass AIProvider(ABC):    @abstractmethod    async def generate(        self,        model: str,        messages: list[dict[str, Any]],        **options    ) -> dict[str, Any]:        pass    @abstractmethod    async def validate_connection(self) -> bool:        pass    @abstractmethod    async def list_models(self) -> list[dict]:        pass
```

Our application will use this interface instead of calling provider SDKs directly from agent code.

That gives us several advantages:

- We can replace a provider without rewriting agents.
- We can compare available models.
- We can track costs and usage.
- We can implement fallback providers.
- We can assign different models to different agents.

One caveat: not every provider supports the same features. We need capability negotiation for streaming, structured outputs, tool calling, image input and other features.

# 6. Agent communication architecture

Let's give this a dedicated subsystem.

I propose two communication mechanisms:

A. Direct messages

For an agent requesting information from another agent.

B. Event broadcasting

For notifying the rest of the system about important changes.

For example:

```
{
  "event_id": "evt_001",
  "event_type": "ARTIFACT_SUBMITTED",
  "project_id": "prj_001",
  "task_id": "tsk_002",
  "sender": "agent_researcher",
  "payload": {
    "artifact_id": "art_001",
    "artifact_type": "research_report"
  },
  "timestamp": "2026-11-08T10:00:00Z"
}
```

The event bus distributes this event to interested services.

The Task Manager might update the task, the Memory Service might index the report, and the Team Leader might receive a notification.

For the first version:

- Redis Streams or a managed message broker for asynchronous events.
- PostgreSQL for durable message and event records.
- WebSockets for live dashboard updates.

Do not make the WebSocket connection the source of truth. It should only deliver updates; the database remains authoritative.

| approvals         | id, task_id, requested_by, status        |

| usage_records     | id, agent_id, provider_id, token_usage   |
| audit_logs        | id, user_id, action, timestamp           |

### Important relationships

- One user can own many projects.
- One project can have multiple teams.
- One team can contain multiple agents.
- One agent can be assigned to multiple tasks over time.
- One task can depend on multiple other tasks.
- One task can generate multiple artifacts.
- One execution can produce multiple messages and logs.

We should use UUID primary keys, foreign keys, indexes and database migrations through Alembic.

For vector retrieval, PostgreSQL with pgvector is a good initial choice. We don't need a separate vector database immediately.

### Command submission example

The user submits:

```
{
  "project_id": "project-uuid",
  "command": "Research the EV market and prepare a business report",
  "preferences": {
    "execution_mode": "hybrid",
    "require_human_approval": true
  }
}
```

The backend returns:

```
{
  "command_id": "command-uuid",
  "workflow_id": "workflow-uuid",
  "status": "planning",
  "message": "Your AI team is preparing the task plan."
}
```

The API should return quickly. It should not wait for all the agents to finish.

Long-running work belongs in the orchestration runtime.

# 9. Human supervision architecture

Our supervised Team Leader needs a proper approval system.

I propose three categories of actions.

| Action category               | Behaviour                          |
| ----------------------------- | ---------------------------------- |
| Routine internal work         | Agents can proceed automatically   |
| Significant project decisions | Team Leader requests user approval |
| External or sensitive actions | Explicit user approval required    |

Examples of approval checkpoints:

- Approving the task plan.
- Connecting a new AI provider.
- Authorising an external action.
- Publishing or sending a generated deliverable.
- Approving unexpected usage above a defined budget.

The user should be able to pause, resume, cancel or redirect a team.

Approvals must be enforced by backend policy checks, not merely by instructions in an agent's prompt.

### How the repository is organised

- `frontend/` contains everything the user interacts with.
- `backend/` contains application logic and API endpoints.
- `orchestration/` controls agent teamwork.
- `runtime/` executes individual agent assignments.
- `integrations/` connects external AI systems.
- `events/` handles communication between internal components.
- `database/` manages persistent data.
- `infrastructure/` contains deployment and operational configuration.
- `shared/` holds contracts used by multiple components.
- `docs/` documents engineering decisions.

One architectural rule: modules should not import each other's internal implementation freely. They should communicate through service interfaces, events or defined contracts.

# 12. Security architecture

Security needs to be designed around the fact that multiple external AI systems will be processing user information.

I would implement these controls from the beginning:

| Area             | Protection                            |
| ---------------- | ------------------------------------- |
| API keys         | Encrypted secret storage              |
| User accounts    | Secure authentication                 |
| Agent tools      | Explicit permission scopes            |
| Project data     | Tenant isolation                      |
| File handling    | Validated uploads and access controls |
| Agent execution  | Sandboxed environments                |
| External actions | Approval checkpoints                  |
| Usage            | Budget limits and quotas              |
| Communication    | Authenticated service requests        |
| Auditing         | Immutable audit records               |

We should additionally defend against prompt injection.

For example, if the Researcher encounters a webpage containing instructions to reveal confidential project information, that content must be treated as untrusted data, not as instructions that override the agent's system rules.

Agents should only receive the information necessary for their assignments.

## 14. What qualifies as our first successful release?

I want a very specific test to define our first working prototype.

MVP acceptance test

User command:

"Research the renewable energy market in Kenya and produce a business opportunity report."

Expected behaviour:

1. Team Leader interprets the command.
2. Team Leader creates a task plan and requests user approval.
3. Researcher and Analyst work concurrently where possible.
4. Agents exchange their findings through the communication system.
5. Creator prepares the report.
6. Critic reviews the report.
7. Team Leader coordinates any necessary revisions.
8. User receives the final report and execution history.

Success criteria

- No lost tasks.
- No uncontrolled duplicate execution.
- Agent communications are traceable.
- User approvals are enforced.
- Final output can be retrieved.
- Usage and execution costs are recorded.

## 15. Important decisions for the first release

There are some features I deliberately would not build immediately:

- A marketplace for third-party agents.
- Hundreds of AI provider integrations.
- Complex autonomous financial transactions.
- Unlimited agent-to-agent conversations.
- A fully distributed microservice architecture.
- Self-modifying agent instructions.

Those features can come later. Our first objective is to prove that a coordinated AI team can reliably complete a meaningful task.
